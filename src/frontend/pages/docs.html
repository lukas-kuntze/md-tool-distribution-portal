Erste Schritte

Vom ersten Projekt bis zur installierten App in sechs Schritten.

  1. Projekt anlegen. Unter Projekte mit „Projekt anlegen“. Ein Projekt bündelt die Apps eines Produkts, z. B. „MEDIFOX DAN - Ambulant“. Dafür braucht es die Rolle Plattform-Admin.
  2. Anwendung anlegen. Im Projekt mit „Anwendung anlegen“: Name, Framework (Flutter oder .NET MAUI), Plattformen und die Paketnamen bzw. Bundle-IDs. Sobald das erste Release existiert, sind diese Kennungen eingefroren. Nutzt die App Flavors (z. B. Production und Staging), werden sie im Tab „Flavors“ angelegt, jeder mit eigenen Kennungen.
  3. Build hochladen. Auf der Anwendungsseite mit „Build hochladen“ oder automatisch aus GitHub Actions (siehe CI-Einrichtung). Version, Build-Nummer und Flavor liest die Plattform aus der Datei. Android- und iOS-Build mit derselben Build-Nummer landen im selben Release; beim manuellen Upload wird zusätzlich der Commit angegeben, aus dem gebaut wurde.
  4. Ergänzen und veröffentlichen. Auf der Release-Seite lassen sich dSYM-, Mapping- und Metadaten-Dateien sowie Release-Notes hinzufügen. „Veröffentlichen“ ist möglich, sobald für jede Plattform der Anwendung ein installierbarer Build vorliegt. „Zurückziehen“ blendet ein Release wieder aus.
  5. Verteilen. Mitarbeitende installieren über Apps installieren. Kunden ohne Konto erhalten im Tab „Freigaben“ einen Freigabelink, auf Wunsch befristet und jederzeit widerrufbar.
  6. Aufräumen. „Release löschen“ (unter „Weitere Aktionen“) verschiebt das Release zunächst in die Quarantäne. Bis zum Ablauf der Frist (standardmäßig 7 Tage) lässt es sich wiederherstellen, danach werden die Dateien endgültig gelöscht.

Installation auf Geräten

Diese Hinweise gelten für Mitarbeitende auf „Apps installieren“ ebenso wie für Kunden mit einem Freigabelink.

phone_iphone iPhone und iPad

  1. Die Seite direkt auf dem Gerät in Safari öffnen; am Computer ist keine Installation möglich.
  2. „Auf diesem Gerät installieren“ tippen und die Rückfrage bestätigen. Der Installationslink gilt nur wenige Minuten; bei einer Fehlermeldung die Seite neu laden.
  3. Erscheint beim ersten Start „Nicht vertrauenswürdiger Entwickler“: Einstellungen → Allgemein → VPN und Geräteverwaltung → das Unternehmensprofil auswählen → „Vertrauen“.
  4. Bricht die Installation ab, ist das Gerät für den Build meist nicht registriert (Ad-hoc-Verteilung). Dann bitte die Geräte-ID an das Projektteam geben.

android Android

  1. Die Seite auf dem Gerät öffnen und den Android-Build (APK) herunterladen.
  2. Beim ersten Mal fragt Android, ob der Browser Apps installieren darf: „Unbekannte Apps installieren“ für diesen Browser erlauben.
  3. Warnt Google Play Protect, über „Details“ → „Trotzdem installieren“ fortfahren, sofern die App aus dieser Plattform stammt.
  4. Updates werden genauso installiert; die vorhandene App und ihre Daten bleiben erhalten.

CI-Einrichtung

Workflows laden Builds über die GitHub Action in src/action/ hoch. Sie melden sich mit dem OIDC-Token ihres Jobs an – es gibt kein Secret zu hinterlegen.

  1. Repository verbinden. Auf der Anwendungsseite im Tab „CI“ mit „Repository verbinden“: Repository als owner/name, dessen numerische ID (abrufbar mit gh api repos/owner/name --jq .id), das Branch- oder Tag-Muster und optional ein Environment.
  2. Workflow anlegen. Den Beispiel-Workflow aus dem Tab „CI“ kopieren; er enthält portal-url und application-id bereits. Der Job braucht permissions: id-token: write.
  3. Ausführen. Der erste Upload einer Build-Nummer legt das Release als Entwurf an; weitere Builds desselben Commits kommen hinzu. Veröffentlicht wird weiterhin im Portal. Ein erneut gestarteter Workflow ist unbedenklich: Bereits gespeicherte Dateien werden erkannt.

Häufige Fehler

Meldung Ursache und Abhilfe
ci_token_invalid (401) Kein oder kein gültiges OIDC-Token: id-token: write fehlt, oder die Audience passt nicht zur Adresse des Portals.
ci_not_bound (403) Keine Anbindung passt: Repository, Branch bzw. Tag oder Environment des Laufs stimmen mit keiner aktiven Anbindung im Tab „CI“ überein.
artifact_commit_mismatch Die Build-Nummer gehört schon zu einem Release aus einem anderen Commit. Build-Nummer erhöhen.
bundle_identifier_mismatch, flavor_mismatch Paketname bzw. Bundle-ID der Datei passt zu keinem Flavor der Anwendung oder nicht zum angegebenen flavor.
artifact_exists (409) Für diese Plattform liegt im Release schon eine andere Datei. Build-Nummer erhöhen oder die alte Datei im Portal entfernen.

Rollen & Rechte

  • Anmelden heißt noch nicht dürfen. Die Mitgliedschaft in der GitHub-Organisation entscheidet nur, ob sich jemand anmelden kann; Rechte gibt es ausschließlich über Rollen.
  • Rollen gelten für einen Bereich – Plattform, Projekt oder Anwendung – und vererben sich nach unten. Hat jemand mehrere Rollen, gilt die Summe.
  • Vergeben werden Rollen unter Benutzer & Zugriff oder im Tab „Zugriff“ eines Projekts bzw. einer Anwendung, immer mit Begründung und auf Wunsch befristet.
Rolle Typischer Bereich Kurz gesagt
Plattform-Admin Plattform Darf alles: Projekte, Benutzer, Rechte, Speicher und Einstellungen.
Projekt-Admin Projekt Verwaltet ein Projekt vollständig: Anwendungen, Flavors, Releases, Rechte, Freigaben, Audit-Log.
Release Manager Projekt oder Anwendung Hochladen, veröffentlichen, zurückziehen, löschen und wiederherstellen.
Entwickler Projekt oder Anwendung Legt Releases an und lädt hoch, veröffentlicht aber nicht.
Tester Projekt oder Anwendung Sieht alle Releases einschließlich Entwürfen und installiert sie.
Betrachter Projekt oder Anwendung Sieht das Projekt und installiert veröffentlichte Releases.

Apps mit der Sichtbarkeit „Organisation“ kann jede angemeldete Person installieren, auch ohne Rolle. Die vollständige Übersicht aller Berechtigungen finden alle, die Rollen vergeben dürfen, unter Benutzer & Zugriff.
